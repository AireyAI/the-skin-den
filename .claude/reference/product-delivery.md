# Product delivery — websites, platforms and staff dashboards

Apply only the sections relevant to this request. Small edits get focused regression checks; substantial features get a short plan and evidence. Never promise perfect first-pass results or claim an unperformed check.

## Establish the product
Read project instructions, current code, approved assets and relevant client notes. Retrieve bounded Obsidian/Graphify context; do not load whole vaults. Identify audience, primary journey, stack, existing providers and acceptance criteria. Reuse known facts. Bundle only genuinely blocking questions. Keep client-specific facts/decisions in the project; no compulsory new paperwork for small edits.

For new sites/platforms record a compact project brief: brand/assets/references, primary action, roles/tenants, integrations, data collected, countries served, legal entity/contact, actual retention/refund/cancellation policies, analytics/embeds, preview/build/test commands. Unknown commercial/legal facts remain unresolved, never invented.

## Design and implement
Automatically delegate substantive visual design to designer (Opus/xhigh). One coherent direction by default, no mandatory three options or ordinary direction approval. Sonnet handles routine fixes and coordination. Preserve client tokens, identity, content and working integrations. frontend-design supplies visual direction; UI UX Pro Max supplies targeted interaction guidance. Do not stack taste frameworks or repeat the designer's work.
Build complete relevant states: loading, empty, validation, success, failure, permission denied and unavailable service. Preserve inputs after errors; prevent duplicate submissions; provide clear recovery. Use semantic HTML, keyboard/focus support, labels, sensible autocomplete, contrast, responsive layouts and reduced motion. Keep useful form help and error/privacy explanations. No invented testimonials or generic filler.

## Website essentials
Select features by visitor journey, not a universal widget list. Verify links, navigation, main CTA and booking/enquiry flow through the actual intended destination using a safe test environment. Preserve booking/payment providers. Add truthful metadata, canonical URLs, sharing images, favicons, crawl rules and structured data appropriate to the build. Keep previews out of search indexing.
Inventory scripts, cookies, local storage, embeds and pixels. Decide consent/exemptions from actual purpose and jurisdiction using current authoritative guidance. Where consent is required, block non-exempt use before choice, offer equally accessible accept/reject, support withdrawal and verify requests/storage after every choice. A banner alone is not proof. Draft privacy/terms only from real client facts; flag unresolved facts and client/legal review. Never copy clinical retention or cancellation rules into an unrelated business.

## Backend and platform essentials
Read existing architecture before changing it. Validate input server-side; enforce authentication, role/ownership and tenant isolation on every relevant server endpoint/database policy. UI hiding is not authorization. Keep secrets server-side; use parameterised queries and least privilege. Test cross-tenant and unauthorised attempts as well as the happy path.
For mutations consider idempotency, duplicate requests, concurrent updates, transaction boundaries and failure recovery. Verify webhook signatures and replay handling where applicable. Define bounded timeouts/retries only for safe operations. Use backward-compatible migrations, recovery plans and realistic test fixtures; never run production migrations or destructive actions without approval.
Log useful structured diagnostics without credentials or personal data. Add health/error visibility appropriate to the existing system, not unsolicited model monitors. Run existing tests and add targeted regression coverage for consequential new behaviour.

## Staff dashboard essentials
Define each role's actual tasks. Prioritise usable navigation, useful tables, search/filter/sort/pagination, timezone/currency accuracy and clear statuses. Preserve selection and unsaved edits where useful. Confirm consequential bulk/destructive actions; show partial failures. Enforce permissions and audit sensitive changes on the server. Check exports for permission scope and spreadsheet formula injection when relevant. Do not expose customer data in logs, URLs or broadly cached responses.

## Verify and finish
Use safe loopback previews of public output. Inspect desktop/mobile and important scrolled/interactive states; check keyboard, zoom/reflow, focus and reduced motion. Target WCAG 2.2 AA; automated scans do not prove complete accessibility. Recheck affected views after fixes, without arbitrary polish loops.
Use available project build/lint/typecheck/tests, browser interaction checks and accessibility tooling. Test backend denials, isolation and failure recovery for relevant changes. Before launches verify actual rendered routes, forms/integrations, metadata/indexing and consent behaviour. Existing ~/Websites completeness tools are optional static-site checks, not universal compliance gates; never call ship.sh --deploy without release approval.
Measure performance proportionally. Aim for real-user p75 LCP <=2.5s, INP <=200ms, CLS <=0.1; lab results are not field evidence. Size/compress assets, reserve dimensions, prioritise main content, limit unnecessary JS/fonts. Do not install heavy tooling for trivial edits.
Report changed files, completed checks, unresolved blockers and local versus deployed state. Do not publish, deploy, spend, send real customer messages or alter production without approval. Deterministic checks run directly; delegate only when the bounded reasoning/summarisation benefit justifies the extra model context.
